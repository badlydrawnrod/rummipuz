# Rummipuz UX improvements and assistance plan

## Status and scope

Planned on 12 October 2026 from user feedback. This document tracks implementation and acceptance. It covers preserving horizontal position, distinguishing red/orange tiles, moving whole rows, collapsing empty rows, making the layout more compact, staying at the chosen difficulty, hints and revealing a solution.

Approved generator revision 6, puzzle rules, physical tile identities and exact revisions 1–6 replay remain unchanged. These changes affect presentation, live layout and assistance. Existing saved sessions and undo history must remain readable. Keep the buildless static app, worker computation and offline support.

This plan takes priority over the remaining finishing checks in the [implementation plan](rummipuz-implementation.md). Complete those browser/device checks against the revised interface rather than repeating them before these changes. Check each item only when its acceptance criteria are met; native checks cannot substitute for the specified desktop/tablet review.

## Intended behaviour

| Request | Planned behaviour |
| --- | --- |
| Horizontal scrolling | Editing a long row preserves the part of that row the player was viewing. Other rows and the rack keep their own positions. |
| Red versus orange | Distinguish the inks more clearly and strengthen a visible cue independent of colour. Logical colours, symbols and names remain consistent. |
| Drag a row | Drag a dedicated row handle to reorder the whole row vertically among board rows. Tile order and contents travel together. |
| Collapse empty rows | Hide emptied board rows and show exactly one New row destination during play. |
| Compact layout | Make the + signs and their visible placement controls smaller, reduce the space they occupy between tiles, and tighten vertical spacing between board rows. Keep tiles readable and placement comfortable on mouse and touch. |
| Difficulty | Start/Next stay at the chosen tier indefinitely. Only a deliberate difficulty choice changes the tier for fresh puzzles. |
| Hint | Show one concrete, explained tile move from the current position, highlighting its source and destination. The player performs it. |
| Reveal solution | Open a clearly labelled, dismissible, read-only complete solution preview. Closing it restores the unchanged play view. |

Row dragging is interpreted as moving a board row before/after another board row, including first/last position. Merging rows or moving a whole row into the rack are outside this first implementation. Reveal displays one valid solution; puzzles can have several. These are implementation defaults to review with the user during the relevant interface steps.

## 1 — Preserve horizontal position

- [x] Fix scroll retention through rendering and overflow refresh. **Done when:** removing or inserting a tile near the middle/end of an overflowing row preserves the visible neighbourhood; editing another row does not reset it. The rack follows the same policy. Test repeated removals, selection, Check, Undo, Reset and viewport resizing. Keep focus changes from scrolling the row unintentionally.

`app/play.js` currently destroys every board-row element in `render()`. `app/overflow.js` can also adjust positions while showing/hiding arrows and exposing placement gaps. Address both paths. Capture positions before DOM replacement and restore them after layout, or retain row elements; do not key retention solely by displayed row number, since empty-row collapse and reordering will change it.

Prefer preserving a visible physical tile and its pixel offset. If that tile disappears, use a surviving neighbour; clamp to the available scroll range when content shrinks. A row viewed at its end should remain at the new end. Rows that now fit need no artificial overflow. Keep arrows and terminal placement gaps correct after restoration. New/replayed puzzles start with fresh viewport state; viewport state need not enter saved puzzle data.

**Verification:** focused rendering/overflow checks plus desktop and tablet removal from the end of a long row. Recheck after steps 3 and 4. Native geometry stubs alone do not establish browser scroll behaviour.

## 2 — Make red and orange easier to distinguish

- [x] Revise tile presentation and review it on both devices. **Done when:** the user can readily tell red and orange apart on a normal display and on their reading/dark display modes, across all app appearances and both palettes. Numbers, symbols and colour names remain readable; selection, dragging and validity cues remain clear. Per user direction, use the selected orange ink even though it is below the previous text-contrast target.

Review `app/styles.css` ink variables and the shared tile/legend rendering in `app/tiles.js`. Choose a clearer hue/lightness separation within text-contrast limits, except for orange which uses the user-selected `#D48519` (10% darker than `#EB941C`). Strengthen the existing heart/triangle distinction with a prominent shape or other simple monochrome cue if colour changes alone are insufficient. Apply the same mapping to board, rack, legend, drag previews, hints and solution previews. Alternative-palette red can retain its established purple mapping; do not change logical tile colours or physical IDs.

Record the chosen inks/cues and contrast results. Include reduced-colour/grayscale inspection, but require user review on the actual limited-colour screen: display reading filters are outside the app's control. Do not assume meeting text contrast proves the two colours distinguishable.

Implementation record (12 October 2026): standard red is `#b51f3e` and orange is `#D48519`; the alternative palette retains purple red `#783e87` and uses the same orange. On the darkest normal tile (`#eee9dc`), calculated WCAG text contrast is 5.36:1 for standard red, 6.11:1 for alternative red, and 2.42:1 for orange. On the light tile (`#fffdf5`), ratios are 6.38:1, 7.27:1, and 2.88:1; on the white high-contrast tile they are 6.50:1, 7.40:1, and 2.93:1. The orange value and colour name use the selected bright ink by user direction, despite the lower contrast. Red's heart and orange's triangle are enlarged from 20px to 26px and bold in both tiles and legend, so the distinction remains shape-coded in grayscale. Visual confirmation on the user's reading display is still required before marking this step complete.

## 3 — Collapse empty rows and establish reliable row targeting

- [x] Render only nonempty board rows and one New row destination. **Done when:** repeatedly emptying several rows leaves no blank row stacks, while every remaining tile and drop target stays usable. Emptying the whole board leaves the single New row target. Undo, Reset, reload and old saved sessions with empty placeholders work correctly.

Existing state intentionally retains empty arrays to keep indices stable. Prefer hiding those placeholders in the view while preserving exact old snapshots; map each visible row explicitly to its state row. Display labels, Check messages, hint text and drop targets must use the same visible-row mapping. New row placement must create or reuse one target consistently, with no duplicated blank destination. Keep transient one/two-tile invalid rows visible.

Before implementation, document how row view identity follows edits, reordering and Undo. Use it for scroll retention and gesture targeting. A displayed ordinal or mutable tile-list string alone is insufficient. If state compaction or persisted row IDs prove necessary, specify backward-compatible save handling first; never rewrite immutable starting puzzles or existing undo snapshots merely for visual cleanup.

**Verification:** tile conservation, hidden-placeholder destination mapping, undo/reset/reload, all-empty board and stale/cancelled gestures. Recheck step 1 after collapsing rows.

Row identity policy (steps 3–4): each play session assigns opaque view IDs to board slots, including hidden empty placeholders. IDs are separate from displayed ordinals and tile contents. Tile edits preserve a slot's ID; New row appends a fresh ID and remains the single visible creation destination. Whole-row reordering explicitly permutes the IDs with their rows. Position-to-ID mappings are retained outside immutable state for Undo and Reset. Reload reconstructs mappings chronologically from the original position, saved history and live position: an unchanged rack plus an exact permutation of complete physical row lists carries row IDs through that permutation; other edits retain slot IDs. Empty placeholders are matched deterministically. An old singleton-to-empty tile move can be indistinguishable from a singleton row reorder in saved positions; reconstruction chooses the same deterministic permutation in either case. Reload starts with fresh viewport state, and live operations retain their precise identity mappings. Neither saves, starting puzzles nor undo snapshots gain fields or lose placeholders.

The session exposes nonempty row views with an ID, actual state index and contiguous visible number. Rendering, placement labels and Check use that mapping; future hints must use it too. UI destinations carry the current position token and board view ID so stale targets are rejected. Scroll snapshots are cached by view ID, including while a row is hidden, so editing another row or undoing an emptied row cannot transfer its viewport to a different row.

Implementation record (12 October 2026): step 3 is implemented without changing puzzle data, save schema or pure move semantics. Offline release is `v9` with the same 39 precached assets. All 1,314 native checks pass, including 15 new session/identity checks and 11 checks exercising the real renderer with simulated geometry: collapse, numbered labels/targets/Check, all-empty board, single New row, Undo/Reset and horizontal anchors. Session checks cover physical inventory, invalid partial rows, stale/cancelled gestures, branched Undo identities and old-format save/reload. Actual-worker and precache-only worker suites pass. The user directed that step 3 be marked complete. No browser was connected during implementation; the automated checks do not establish desktop/tablet scroll behaviour. The collapse walkthrough in the project README remains available for integration review in step 8.

## 4 — Drag whole rows to reorder the board

- [x] Add an undoable row-reorder operation. **Done when:** a drop moves one complete nonempty row to a valid insertion position, preserving every physical tile and its order, all other rows, the rack and initial puzzle. One reorder adds one undo entry; dropping back at the same position is a no-op. Undo/Reset and save/reload restore exact ordering.
- [x] Add mouse and touch row handles and insertion previews. **Done when:** the player can comfortably move a row to the top, middle or bottom, including across a vertically scrolling board, on desktop and tablet. Dragging from the handle cannot accidentally move one tile, activate a placement gap or hijack ordinary row scrolling. Cancelling or dropping outside a destination leaves the puzzle unchanged.

Add a pure operation in `app/state.js`, exposed through the play session. Treat whole-row dragging as distinct from tile dragging. Use one dedicated six-dot grip on the left of each stationary row header, beside the row label, with a 48×48px touch target, visible insertion marker, vertical edge scrolling and a deliberate activation gesture. Retain horizontal position for the moved row and unaffected rows. Do not allow reordering after completion is locked. Per the user-approved refinement, use a single drag handle and remove the Up/Down alternatives. A dedicated keyboard gameplay system remains outside this step.

**Verification:** first/last/upward/downward insertion indices, no-ops, inventory, immutable snapshots, exact undo and persisted order; mouse/touch gesture separation and cancellation; interactions with hidden empty rows and scrolled rows.

Step 4 implementation design: the pure operation uses a pre-removal board insertion gap, including hidden placeholders. The session exposes destinations relative to stable visible row IDs (before a row, or after the last visible row), stamped with the current position token. A drop into the same visible position is a no-op even if hidden placeholders lie between the source and destination. Headers stay outside horizontal tile scrollers and provide one six-dot drag grip on the left, followed by the row label. Mouse dragging starts after deliberate motion; touch dragging starts after a brief hold. The row controller is separate from tile dragging, shows a row-label preview and insertion marker, and scrolls vertically near viewport edges. Cancellation or any intervening state change invalidates the gesture.

Reordering carries row IDs and horizontal viewport anchors with the rows, and invalidates earlier tile destinations and pending solution requests. Initial puzzles, save schema and existing undo snapshots remain unchanged. Offline release is `v11` with 40 precached assets, including `row-drag.js`. All 1,377 native checks pass: 87 core, 66 session, 18 renderer and 29 row-gesture checks, alongside tile-touch, overflow, replay/save and actual-worker/precache-only suites. ## 6 — Reveal a verified complete solution

- [x] Add a cancellable solution request for the current puzzle and a Reveal solution preview. **Done when:** the preview shows every puzzle tile exactly once in valid rows, with an empty rack, and uses the common tile palette/appearance. It is usable on desktop and tablet, including long rows, and closes back to the exact live arrangement, selection, undo history and view position. Revealing alone neither completes the puzzle nor writes completion credit.

The existing worker-backed solver can solve the conserved inventory even when the live board is temporarily invalid. Use a bounded request and verify its physical output with the rules module. Reject corrupt inventory and distinguish cancellation, exhausted work and a proved lack of solution. A supported published puzzle should remain solvable after legal tile moves; an unexpected failure needs clear retry feedback, not a fabricated answer.

Prefer a solution compatible with the current layout when feasible, sharing the assistance machinery in step 7. A valid stored witness may be used only after verifying its identity/inventory; restored sessions may lack witness metadata, so they must work without it. All solution computation remains in a worker, with cancellation and main-thread responsiveness.

The preview is a separate labelled panel/dialog, not a replacement live board. Provide Close, sensible focus return and accessible tile/row labels. No automatic Apply solution action is included. The player may continue, Reset, manually follow the preview or choose another puzzle. Existing Check remains the completion action.

## 7 — Give one sensible hint from the current position

Approved interaction design (12 October 2026): Hint sits beside Reveal solution and opens a compact inline card below the play controls. The card gives one concrete move and a short reason, with distinct source/destination outlines on the exact physical tile and insertion gap. Show tile and Show destination reveal only the requested area; no automatic selection, placement or scrolling is performed. Dismiss cancels pending work and closes the card. Repeated requests without a position change return the same advice. Any move, row reorder, Undo, Reset or replacement clears the old hint; a ready-to-win position says Select Check to finish. Search remains cancellable in a worker while ordinary play stays available, with truthful limit/error feedback and bounded retry. Hint and Reveal share a verified preferred target, while later requests still consider the player's current progress.

- [x] Implement and verify a deterministic current-position assistance planner. **Done when:** it chooses a conserved complete target and derives a finite legal tile-move sequence from the actual live arrangement. Applying that sequence reaches the verified target. It handles duplicate faces as distinct physical tiles, invalid intermediate rows, partial player progress and necessary temporary rack staging.
- [x] Add Hint with concise move text and source/destination highlights. **User-approved on 12 October 2026.** **Done when:** one click shows one actionable next move, such as “Move Orange 8 from row 3 into row 1 between 7 and 9,” plus a brief reason. The intended physical copy and insertion gap are unambiguous. The player performs the move through ordinary controls; requesting a hint does not mutate state or add undo history.

`app/solver.js` currently ignores current placement and stored solutions. Its first complete partition is not by itself a useful hint. Add current-layout preferences in a separate assistance path: preserve completed valid sets and useful partial work where compatible with a solution, prefer a rack placement or a productive rearrangement, and avoid reversing the player's work merely because an equivalent group has another colour order. Treat these as bounded heuristics, not a guarantee of globally optimal or human-easiest play.

Derive insertion destinations against the current state, not the initial board or a stale hint. If a temporary move to the rack is necessary, explain what it frees or prepares. Suppress no-op, pure cosmetic reorder and immediate back-and-forth hints. Repeated Hint without a state change returns the same instruction; after the player moves, recompute from the new position. Do not require blindly following a precomputed witness.

Hints and Reveal requests must carry puzzle/state identity tokens. Any tile move, row reorder, Undo, Reset, replay or session replacement cancels or invalidates pending results/highlights. A limit/failure leaves the live state intact and offers retry; it must not be called “no solution” unless proved. A board already ready to win gets “Select Check to finish”; completed sessions need no hint. Resolve offscreen highlighting through deliberate reveal of the hinted source/target, keeping unrelated rows' viewports unchanged.

**Verification:** replayable fixtures from all four tiers and revisions 1–6, partial valid work, temporary invalid rows, repeated physical faces, all tiles temporarily in the rack, hidden placeholders, reordered/scrolled rows, work-limit/cancellation races and stale responses. Replay every proposed move sequence through the real state operations and independently check the final win. Review the usefulness of hints with the user; solver validity alone does not establish sensible advice.

Initial hint search permits 200,000 nodes; retry after a work limit permits 1,000,000. State identity and abort guards discard stale results.
